Building "The Choicer Voicer Launcher.exe" from source
========================================================

Plain C using the native Win32 API, plus the vendored miniz library
(public domain) for reading .zip files. RAR extraction shells out to
7-Zip or WinRAR if either is installed - no bundled RAR decoder.

On Windows, with mingw-w64 installed (e.g. via MSYS2, MinGW64 shell):

    windres resource.rc -O coff -o resource.o
    gcc -municode -O2 main.c resource.o miniz/miniz.c miniz/miniz_tinfl.c miniz/miniz_tdef.c miniz/miniz_zip.c -o "The Choicer Voicer Launcher.exe" -mwindows -lcomctl32 -lshell32 -lole32 -luuid -lwininet -ldwmapi -luxtheme -lcomdlg32 -lgdi32 -luser32 -s -I miniz

(Added since the last version: -lole32 -luuid for OLE drag-drop of
dragged web links, -lwininet for downloading mods, -ldwmapi for the
dark titlebar, -luxtheme for dark-themed dropdowns.)

Files:
  main.c          - the launcher's window/logic
  resource.rc     - embeds sideimage.bmp, appicon.ico, and manifest.xml
  manifest.xml    - turns on themed buttons/group boxes + DPI awareness
  sideimage.bmp   - the character art shown on the left of the launcher
  appicon.ico     - the launcher's own taskbar/exe icon
  miniz/          - vendored miniz (public domain), reads .zip files in-memory

REQUIRED FOLDER LAYOUT next to the launcher exe:

  <launcher folder>\
    The Choicer Voicer Launcher.exe
    launcher_settings.ini   <- auto-created/updated by the launcher itself
    Normal\
      <any folder name>\
        YourGame.exe
        display.txt         <- shows up as the dropdown label
    Compatibility\
      <any folder name>\
        YourGame.exe
        display.txt

launcher_settings.ini is written automatically - you don't need to
create it. It stores which version you last launched in each mode
(pre-selected on next open) and whether Dark Mode is on.

FIXED: title/subtitle text and the Normal/Compatibility Mode card
borders were disappearing. Cause: those controls were made
WS_EX_TRANSPARENT so the animated backdrop would show through them,
but the window also has WS_CLIPCHILDREN (added to stop the animation
from flickering the buttons) - and WS_CLIPCHILDREN blocks exactly the
"let the parent paint behind me" mechanism WS_EX_TRANSPARENT depends
on. Those two don't coexist reliably. Fix: labels/group boxes/checkbox/
drop zone now use a solid (not see-through) panel background again.
The animated stars still show in the actual gaps between elements -
just not directly behind text anymore.

FIXED: toggling Dark Mode didn't actually recolor the labels/buttons -
only the checkbox itself updated. Cause: after rebuilding the theme
brushes, I only invalidated the top-level window, not its child
controls (labels, group boxes, buttons are all separate windows that
don't repaint just because their parent did). Fix: ApplyThemeColors
now uses RedrawWindow(..., RDW_ALLCHILDREN | RDW_UPDATENOW) to force
every child control to actually repaint immediately when the theme
changes.

FIXED: the Normal Mode / Compatibility Mode card interiors stayed
white in dark mode even though the title strip changed. Cause: native
BS_GROUPBOX is theme-drawn - its border+title respect WM_CTLCOLORBTN,
but its interior fill does not, and is left to whatever was painted
underneath at creation time. Fix: MakeGroupBox no longer uses
BS_GROUPBOX at all - it's now a plain bordered STATIC panel (which
fills its whole rect correctly, same as the title/subtitle labels)
with a separate title label drawn on top.

FIXED: the (i) info icon's tooltip never appeared on hover. Cause:
InitCommonControlsEx() was only asked to register ICC_STANDARD_CLASSES,
which doesn't include the tooltip control - so creating a TOOLTIPS_CLASS
window silently failed (returned NULL, which the code checked for and
quietly skipped, so nothing crashed - it just never worked). Fix: added
ICC_WIN95_CLASSES to the requested classes, which covers tooltips.

REPLACED: the (i) info tooltip. Two attempts using the native Win32
tooltip common control (TOOLTIPS_CLASS) didn't show anything on hover,
and without a live Windows box to attach a debugger to, further blind
tweaking of TOOLINFO flags wasn't a reliable path forward. Replaced it
with a small custom popup window built and controlled directly (its
own window class + WM_PAINT drawing + shown/hidden via mouse hover
tracking on the icon) - no dependency on common-control tooltip
internals at all.

NEW: "Browse Mods" tab. A tab row (Launcher / Browse Mods) now sits
above the header. Browse Mods talks to GameBanana's public JSON API
(gamebanana.com/apiv11/Mod/Index, filtered to this launcher's
configured game id) on a background thread so the UI doesn't freeze,
shows a scrollable list of mods with a thumbnail, name, and author per
row, and an "Install" button per row that feeds straight into the same
download/extract/install pipeline the drop zone already uses (so it
respects whichever pack folder is currently selected). Thumbnails
(JPG/PNG) are decoded via WIC (Windows Imaging Component), which is
built into Windows itself - no new library is bundled or linked for
this; CoCreateInstance loads windowscodecs.dll from the OS at runtime.
`#include <initguid.h>` was added directly before `#include
<wincodec.h>` so the WIC GUIDs are defined in this object file rather
than depending on them being present in the installed MinGW
distribution's libuuid.a - no new linker flags are required for any of
this. Switching tabs just shows/hides two mutually-exclusive halves of
the window (the Launcher tab's real controls are tracked in an array;
its "transparent" title/subtitle/tip text has its own show/hide flag
since it's drawn straight onto the backdrop rather than being real
windows) - nothing about the Launcher tab's own behavior changed.
This talks to the live GameBanana API and downloads live thumbnail
images, which I can't fully test from here - if GameBanana ever
changes their API response shape, the mod list may need adjusting.

FIXED: build failed with "cc1.exe: fatal error: minizminiz.c: No such
file or directory". Cause: the build command used Windows-style
backslashes (miniz\miniz.c), but MSYS2's MinGW64 shell is bash, and
bash treats \m as an escape sequence - it drops the backslash and
keeps the m, turning "miniz\miniz.c" into "minizminiz.c" before gcc
ever sees it. (Backslashes are fine in cmd.exe, just not in this
bash-based shell.) Fixed by switching to forward slashes in the build
command, which mingw's gcc/windres accept fine on Windows regardless
of which shell you're building from.

This was never a "no mods found" problem, a blocked/bot-detected
request, or a caching artifact - just one invalid query parameter
causing the API to refuse the whole request every time. Browse Mods
should work correctly now.

FIXED: Browse Mods effectively "getting stuck" always showing the same
20 newest mods no matter how many times Load More was clicked. Root
cause: MOD_FETCH_MAX_RAW_PAGES was only 25 (1,250 raw items scanned per
fetch). Directly querying GameBanana's Mod/Index API confirmed (again)
that it ignores every _aFilters[...] parameter regardless of value -
one test came back with "_nRecordCount": 548392 (GameBanana's TOTAL mod
count across every game on the site) mixed with results from several
completely unrelated games, proving the filter did nothing at all. So
finding this game's mods means walking the raw, unfiltered "newest
across all games" feed and filtering client-side - and since this
game's mods are a small fraction of that global feed, they can cluster
and thin out unpredictably. Once a sparse stretch was hit, a single
fetch's small budget could come back with 0 new matches, over and
over, which looked exactly like "stuck on the same 20" even though the
underlying page-walking logic itself was advancing correctly. Raised
the budget to 150 raw pages (7,500 items) per fetch - it runs on a
background thread either way, so a slower fetch never freezes the UI.

NEW: real page tabs (Prev / 1 2 3... / Next) at the bottom of the
Browse Mods list, replacing the old "Load more mods..." text link.
Each numbered tab is a page of 20 mods out of the current search/sort
results (not a raw GameBanana page - see MOD_FETCH_RAW_PERPAGE /
MOD_FETCH_MAX_RAW_PAGES for that). Clicking a page you've already
loaded just jumps to it instantly; clicking Next past the last loaded
page triggers fetching another batch (shows "Loading mods..." in the
same bar) and automatically lands on it once it arrives.

Two things worth knowing about the fetch/pagination approach here,
since I can't run this to watch it end-to-end myself:
- GameBanana does document a per-game endpoint that looks purpose-built
  for exactly this (apiv11/Game/:id/Subfeed) - I found it referenced in
  third-party API documentation, but couldn't fetch it directly with
  this game's ID from this sandboxed environment to confirm its real
  response shape, so I didn't want to rewrite the fetch around an
  unverified endpoint. If Browse Mods is still unreliable after this
  change, that endpoint is worth trying next - it should be more direct
  and efficient than walking the global feed if it works as documented.
- A very large raw-page budget means a "Load More"/Next-page fetch can
  legitimately take a while (multiple seconds) if this game's mods are
  sparse in a particular stretch of the global feed. That's expected,
  not a hang - the "Loading mods..." status in the page bar should
  still be visible and responsive while it works.

FIXED: "Next" was clickable, but after a long wait it did nothing and
the whole page bar vanished, replaced by an error message with no
Prev/page-numbers/Next at all - even though mods had already loaded
successfully before that click.

Two things going on:

1. Root cause of the failure itself: MOD_FETCH_MAX_RAW_PAGES was 150.
   That's up to 150 HTTP requests in a single "Next" click, each
   potentially followed by a thumbnail download for every match found
   - very likely enough sustained rapid-fire traffic to trigger
   GameBanana's own rate-limiting, which would explain both the long
   wait (throttled/slow responses) and the eventual outright failure
   (requests started getting rejected). Lowered the cap to 30 pages -
   given the ~40-50% match rate seen for this game in GameBanana's
   "newest" feed, that's still generous - and added a 200ms pause
   between each page fetch within a scan, so a multi-page search
   doesn't hammer the API in a tight loop.

2. The actual bug in how a failure was handled: any fetch failure -
   including one triggered by clicking Next for MORE mods, with plenty
   already loaded and browsable - set the same MODLOAD_ERROR state
   that fully replaces the page bar with a bare error message. That's
   correct for a genuine first-load failure (nothing to browse yet,
   so an error+retry screen makes sense), but wrong for a failed
   "load more": it threw away navigation to content that had already
   loaded fine. Now a failed fetch only takes over the whole page bar
   when nothing has loaded yet (g_modCount == 0). If mods are already
   loaded, it stays in the normal LOADED state - Prev/page-numbers
   keep working, and hasMore is left TRUE so clicking Next again
   simply retries the fetch instead of leaving you stranded.

FIXED: search and the "Most Liked"/"Most Viewed" sorts were only ever
reordering/filtering whatever mods happened to already be loaded into
the local cache - not actually querying GameBanana's full catalog for
this game. This wasn't really a bug in the old code so much as a real
gap: sort was client-side because I didn't have a confirmed-working
_sSort value, and search never had confirmed server syntax at all.

Fixed the sort half with real data: a request captured directly from
GameBanana's own browser network traffic confirmed two things at once
- the API is actually on apiv13 (not apiv11, which the code had been
using this whole time), and _sSort=Generic_MostViewed is a genuine,
working parameter. Changes:

  - Switched the fetch URL from apiv11 to apiv13.
  - apiv13 also changed its thumbnail field shape - _aPreviewContent.
    screenshot._sBaseUrl/_sFile220 replaces the old _aPreviewMedia.
    _aImages[]._sBaseUrl/_sFile100. Updated the parsing to match.
  - Sort mode now flows through to the fetch thread. Likes and Views
    request _sSort=Generic_MostLiked / _sSort=Generic_MostViewed from
    the server; Newest and Name still have no server equivalent
    (Newest is just the default order with _sSort omitted, and Name
    isn't a GameBanana concept), so those two stay a pure client-side
    resort - which is correct either way, since re-sorting a cached
    set by its own real stored date/name works regardless of what
    order it was originally fetched in.
  - Switching TO Likes or Views now clears the cache and does a fresh
    fetch in that real server order, instead of just re-sorting
    whatever was already loaded (which was the actual bug the user
    was seeing - "most liked among an arbitrary newest-biased sample"
    isn't the same thing as "most liked overall").

Only _sSort=Generic_MostViewed is independently confirmed (captured
directly from a real browser request). Generic_MostLiked is inferred
from the same "Generic_<Name>" naming convention seen consistently
across Generic_Category/Generic_Game/Generic_MostViewed - a
reasonable bet, but not verified the same way. If "Most Liked"
produces an UNKNOWN_SORT-style error or silently ignores the sort,
that's the first thing to check - capture the real request from a
browser doing that specific sort and it can be corrected in one pass.

Search is still client-side-only - no confirmed search endpoint or
parameter names surfaced during this pass. If that's wanted next,
the same approach that solved sort will solve it: use the site's own
search box in a real browser, check DevTools -> Network for the
request GameBanana's frontend actually sends, and share that URL.

FIXED: switching to Sort: Newest after having been on Most Liked/Most
Viewed broke both the sort order itself and pagination, persisting
until relaunch. Root cause: only Likes/Views were triggering a fresh
fetch on sort change - Newest fell through to a local re-sort of
whatever was already cached. But that cache was populated by the
Likes/Views fetch, meaning "Newest" was just re-sorting the top-N
MOST-LIKED mods by date - a small, biased subset, not the actual
newest mods for the game. Worse, g_modNextPage was left pointing at
wherever the Likes/Views pagination sequence had gotten to, so the
next "Load More" continued that stale sequence instead of starting
the Newest query's own pagination from page 1 - which is what
persisted incorrectly until the app restarted and reset that state.

Fix: every sort change now does the same clean cache-clear + fresh
fetch, including switching to Newest - there's no longer a "just
re-sort what's cached" path for any sort mode.

REMOVED: Sort: Name (A-Z) - never had a real server-side equivalent
and evidently didn't work as wanted, so removed per request rather
than continuing to carry a broken option. Sort is now Newest/Most
Liked/Most Viewed only; the enum and combo box list were kept in
sync (both now 0=Newest, 1=Likes, 2=Views).

NEW: "+ Add Version" button under each mode's dropdown (Normal Mode and
Compatibility Mode), inside the same card as that dropdown. Clicking it
opens a small popup:
- "Browse..." opens a standard Windows file-open dialog (GetOpenFileNameW)
  filtered to .exe files - this needed a new library, comdlg32, added to
  the build command below (-lcomdlg32). No other new dependency.
- A version-number field, strictly validated as #.#.# (one or more digits,
  a dot, one or more digits, a dot, one or more digits - nothing else;
  "1.5.3" and "10.0.1" are fine, "1.5", "v1.5.3", "1.5.3.1" are rejected
  with a message box explaining why).
- Two checkboxes that must both be ticked before "Add Version" does
  anything: confirming the EXE is actually the Normal/Compatibility
  version (whichever card the button was clicked from), and confirming
  the launcher's own EXE lives in its own separate, isolated folder (not
  inside the Normal/ or Compatibility/ folder itself).

On confirm, it creates Normal/<version>/ or Compatibility/<version>/
next to the launcher EXE (refuses and asks for a different version
number if that folder already exists - never silently overwrites),
copies the chosen EXE into it under its original filename, and writes
a display.txt containing the same version text - the exact layout
ScanVersionFolder/ReadDisplayNameTxt already expect from a manually
dropped-in version, so the dropdown picks it up and shows it the same
way as any other version, no special-casing needed. The dropdown and
Launch button refresh immediately and the new version is auto-selected.

Both cards' layout already had a few pixels of slack below the
combo/Launch row (Normal Mode: 130 to 242, row ends at 200; Compatibility
Mode: 260 to 372, row ends at 330) - the new button fits inside that
existing space, so no card resizing or downstream layout shift was
needed.

FIXED: the Dark Mode button being covered by the Browse Mods tab's list
window. Cause: Dark Mode was floating in the content area at (675, 20),
which is the exact same top-left corner the Browse Mods list window
gets created at - and since that list window is a real, opaque sibling
window created afterward in WM_CREATE (later siblings default to a
higher z-order than earlier ones), it was drawing right on top of the
Dark Mode button the moment the Browse Mods tab was opened.

Rather than just nudging Dark Mode's coordinates to dodge the list
window again (fragile - the next layout change could reintroduce the
same class of bug), it was moved into the left sidebar as an icon-only
toggle (\u2600 sun / \u263E moon for light/dark) at (10, 164), right under the
Browse icon. The sidebar is the one part of the window already
guaranteed to stay visible and unobstructed on every tab - the same
reason the Launcher/Browse/Modding Folder/Info buttons already live
there - so this is a permanent fix rather than another coordinate
patch.

FIXED: messy-looking Info and Modding Folder icons in the sidebar.
- Info button: it was drawing its own circular background (via Ellipse)
  AND the Unicode "circled i" character (U+24D8), which already has its
  own circle baked into the glyph - two slightly different-sized,
  misaligned circles stacked on each other. Replaced the glyph with a
  hand-drawn dot-and-stem "i" (a small Ellipse plus a RoundRect), so the
  button's own circle is the only circle.
- Folder icon: the two pieces (tab and body) were both plain
  sharp-cornered Rectangles, with the tab flush against the body's left
  edge - looked like two stacked boxes rather than a folder. Both are
  now RoundRect with the tab inset from the body's left edge, closer to
  an actual folder tab's proportions.
